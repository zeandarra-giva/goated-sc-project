How Scope Copilot will use AI,
and what ships if it can't

We are not building or training a model. Scope will call a model that Citi has already approved, through Citi's approved AI gateway. Scope does the rest itself: it finds the facts, removes personal data, checks the model's answer and keeps an audit trail. A person still makes every change in ServiceNow. If AI is not approved, or the gateway is down, Scope runs in rules-only mode with the same knowledge base, data and screens.

What we buildRetrieval, redaction, prompt templates, answer checks, audit logs and the UI. All of this is ordinary application code, so it can be tested.
What we callAn approved model endpoint, using the firm's gateway, credentials and data-handling terms. We never host, fine-tune or train a model.
What ships without AIExplorer (Tier 1), Template search (Tier 2), KB search, Resolution Assist and automated insights. All of these already work in the prototype with no model.
01 · Principles

Six rules the design follows

Every later choice in this plan comes from one of these. They also double as the answers to the questions a model-risk or InfoSec reviewer usually asks first.

P1

Use, don't build

Only models and endpoints already on Citi's approved list. Switching to a different one is a config change, not a code change. Scope adds no model weights, fine-tuning or embeddings service of its own.

P2

Scope fetches, the model writes

Scope decides which tools to run and collects the evidence itself. The model only turns that evidence into a readable answer. It cannot query systems on its own.

P3

Send the least data

Only the passages and fields one question needs. Names, emails, SOEIDs and phone numbers are swapped for placeholders before anything leaves Scope.

P4

Cite it or don't say it

Every claim must point to a KB passage, ticket or data row that Scope sent. Every number must match a tool result. If an answer fails these checks, it is not shown.

P5

A person acts

Copilot proposes. Fixes go to a team lead for approval, and drafts are copied by a person. Nothing is sent or changed in ServiceNow without a human click.

P6

Off is a supported state

Rules-only mode is a complete product, not an error page. One switch turns AI off for everyone, and the Copilot page keeps working with search and templates.

02 · Architecture

Where the AI sits, and what stays inside Scope

Most of the system is Scope's own code. The model is one box behind the gateway, and only redacted evidence crosses into it. Use the switch to see which path is used when AI is not approved.

The model writes the answer from the evidence Scope collected. Rules mode is on standby.
  1. 1Ask. The question goes to the orchestrator, with the user's SOEID, role, and the ticket or insight it was asked from. The orchestrator classifies the intent and chooses the tools.
  2. 2Retrieve. Scope runs those tools against the KB, data tables, ServiceNow and history, using the asking user's permissions. This step is the same with or without AI.
  3. 3Send. The evidence is minimised and redacted, then wrapped in a fixed prompt template and sent through the gateway. The gateway, not Scope, holds the model credentials.
  4. 4Draft. The model returns structured JSON: answer parts, plus the evidence IDs it used for each one. It has no tools and no memory between calls.
  5. 5Check and show. Scope checks the citations, numbers and actions. Only an answer that passes is shown, together with its steps and sources. A failed check falls back to the rules answer.
  6. RRules path. With no AI, the rules engine writes the answer from the same evidence. It uses fixed templates, so the wording is plainer but the facts and sources are the same.
  7. 6Act. A person approves the fix or copies the draft. Only after that does Scope write to ServiceNow, and the change is audited the same way as a manual one.
03 · Under the hood

What the model actually does with our input

A large language model doesn't look anything up and doesn't learn from our tickets. It reads the text Scope sends, then predicts a reply one token at a time. The quality of an answer therefore depends mostly on what Scope puts in the prompt, which is why most of the engineering work is retrieval and checking, not the model.

Step A · Input

Text becomes tokens

The prompt is cut into tokens, which are word pieces. The model reads all of them together in one "context window". It sees nothing outside this window.

You helpSolutionCenteranalysts… [RB-112#2]Pushthe VPNprofilereset… Howdo Ifixthis?

instructions evidence question

Step B · Processing

Predict the next token

Layers of attention weigh every token against every other token. The output is a probability for each possible next token. A low temperature (we use 0–0.2) makes it pick the most likely one, so answers stay consistent.

profile0.82
client0.11
certificate0.05
…0.02
Step C · Output

Tokens become a structured answer

It repeats until the answer is complete. We ask for JSON in a fixed schema, which means Scope can check the answer, not just display it.

{ "parts": [{ "text": "Push the VPN profile reset…",
             "cites": ["RB-112#2"] }],
  "action": "request_fix:NET-VPN-01" }

What the model does

  • Reads the redacted evidence and the question, and writes a clear answer in the order an analyst needs it: next action first, then context.
  • Joins facts from several sources, for example the runbook steps, the ticket's SLA timer and the on-call owner.
  • Rewrites for different readers: a customer update, a shift handover, a team-lead summary.
  • Tags each sentence with the evidence IDs it came from.

What it never does

  • Query ServiceNow, the KB or any system. Scope's tool runner does that before the call.
  • Remember earlier chats or learn from them. Each call is stateless, and the gateway terms forbid training on our data.
  • Act. It can only suggest one of a short list of allowed actions, and a person approves each one.
  • Supply the numbers. SLA timers, counts and MTTR come from tools; numbers it makes up fail the checks.
Why retrieval and not fine-tuningThis pattern is called retrieval-augmented generation (RAG). Our knowledge changes daily: runbooks get edited, on-call rotates and apps degrade. If the knowledge were trained into a model, every change would mean retraining, and the model would need its own model-risk review. With retrieval, a KB edit is live once it is published and indexed, and the model itself never changes.

05 · Step-by-step implementation

Rollout: rules first, AI behind gates

Phases 0–2 deliver value whether or not AI is ever approved. The AI work starts only after the governance gate, and each later phase has an exit test that has to pass before more users get access.

PHASE 0
Governance and intake
No AI calls yet

Do

  • Register the use case with Citi's AI governance and model-risk process (forum names to confirm).
  • Classify the data: ticket text, caller details, KB content, metrics.
  • Pick the model and endpoint from the approved list. Confirm the retention and no-training terms.
  • Write the threat model: prompt injection through KB pages and ticket text, data leakage, over-reliance.

Output

  • Approved use-case record and data classification
  • Agreed fields that may and may not be sent
  • An evaluation plan with acceptance thresholds
Gate: approval to build against the gateway in a non-production environment. If refused, skip to Phase 2 and stay rules-only.
PHASE 1
Knowledge base and data foundation
Ships without AI

Do

  • KB with draft → review → publish → index, owners and review dates.
  • Migrate runbooks, policies and known errors. Link each resolution code to its runbook.
  • Data tables (app directory, on-call) synced from CMDB and the rota.
  • History store for resolved tickets (SC Lakehouse, TBC).

Output

  • A search index of published passages only
  • KB Health: conflicts, gaps, stale pages
Gate: every resolution code used in the last 90 days has a published runbook, and no unresolved policy conflicts remain.
PHASE 2
Rules-only Copilot and tool APIs
Ships without AI

Do

  • Build the tool runner as read-only APIs that run with the asking user's ServiceNow and KB permissions.
  • Intent router and template answers (the prototype's "Rules only" model option).
  • Explorer (Tier 1), Template search (Tier 2), Resolution Assist, automated insights.
  • Audit log and feature-flag kill switch.

Output

  • A complete product with no model dependency
  • A logged set of real questions (misses included) to use as the evaluation set
Gate: analysts use it in a live shift. Questions that didn't get a good answer are recorded on the KB Health tab.
PHASE 3
Gateway integration in a sandbox
AI · non-prod

Do

  • Gateway client with timeouts, retries and token budgets, plus a pinned model version.
  • Redaction, the prompt templates, and the JSON schema for answers.
  • Answer checks: citation IDs, numbers against tool results, action allow-list.
  • Run the evaluation set from Phase 2, plus red-team prompts (injection in KB pages and ticket text).

Output

  • An evaluation report: correctness, citation rate, refusal rate, latency, cost
  • A side-by-side comparison with rules-only answers
Gate: the thresholds from Phase 0 are met, there is zero PII in the gateway logs, and model risk signs off.
PHASE 4
Shadow, then pilot
AI · limited users

Do

  • Shadow: the AI answer is generated and logged but not shown. Reviewers compare it with the rules answer.
  • Pilot: one team, the Copilot page only, with the "AI-generated" label and a thumbs up/down on every answer.
  • Weekly review of flagged answers with the KB owners.

Output

  • Pilot metrics: time to the first useful action, FCR, how many answers needed correction
Gate: no critical incidents, the agreed accuracy is met, and the pilot team wants to keep it.
PHASE 5
General availability and monitoring
AI · all users

Do

  • Turn it on in the ticket workspace and on Reports insight cards.
  • Monitoring: check failures, latency, cost, drift in the feedback, gateway errors.
  • Revalidate when the model version changes, and do a periodic model-risk review.

Output

  • A runbook for the AI feature itself, including the kill switch
Always: any breach of a control flips it to rules-only automatically. Users see a banner, not an error.

Tier 2 · Template search, live

This runs the same rules as parseQuery() in src/analytics.js. Type a question and see how it is turned into a query. No model is involved: it is keyword patterns mapped onto three templates.

How the other rules-based parts work

Tier 1 · Explorer deterministic

The analyst picks a measure (volume, RES/EZE MTTR, lost time, SLA attainment, FCR, transfer rate, under-4h goal), a dimension (channel, app, product group, assignment group, analyst, root cause, code, priority, week), a window and a priority. Scope groups the resolved tickets and computes the measure for each group.

rows = inWindow(history, now, days, prio) groups = groupBy(rows, DIMENSIONS[dim].get) value(g) = MEASURES[measure].fn(g) // e.g. avg(resH)

Template search is just a text front-end to this same function.

Ticket Explorer deterministic

This is a browsable record of resolved tickets, not a search engine. It has filters, a five-step journey per ticket, resolution codes that open as tabs with their runbook, stats and tickets, and a handover log. It answers "what happened", and the analyst does the reading.

  • Ticket tab: header, journey, similar incidents, code
  • Code tab: uses, MTTR, FCR, runbook steps, apps

KB search deterministic

Published pages are split into chunks at each ## heading. Attachments are chunks too, and internal notes never are. Words are lower-cased, stop words are dropped, and long words are stemmed.

score(chunk) = Σ over query terms +1 if the term is in the chunk +1.5 if the term is in the page title +4 if a code/runbook ID in the query is on the page +0.3 for "Steps", "Workaround", "Resolution targets" score ÷= max(2, number of terms) keep score ≥ 0.34, top 4

With AI, this is still the retrieval step. Without AI, these passages are the answer.

Resolution Assist deterministic

It compares the open ticket's description with every resolved ticket by keyword overlap. Close matches vote for the code they were resolved with.

sim(a, b) = |words(a) ∩ words(b)| ÷ min(|a|, |b|) similar = history where sim > 0.25, best first votes[code] += sim (top 25) confidence = votes[code] ÷ Σ votes

Output: the likely code with its confidence, typical RES time, FCR rate, similar incidents, the runbook, and an automated fix to propose for team-lead approval.

Why the fallback is easier to approveEvery output can be explained by a formula and a list of inputs. Nothing generates new text beyond templates, no data leaves Scope's boundary, and the same input always gives the same result. That usually puts it in the standard application change process, not the model-risk process. Confirm this with governance in Phase 0.

08 · Token budget

How many tokens Copilot will use

An estimate for the design in section 04, where Scope collects the evidence and the model is called once per question. That means tokens scale with how many questions are asked, not with how many tickets come in. The sizes below are measured from the prototype. The usage volumes are assumptions: replace them with the question log from Phase 2.

Uses tokens

Only step 6, Call the model. That covers Copilot answers on the Copilot page and in the ticket workspace, including "Ask why" on an insight card.

Uses none

Explorer, Template search, KB search, Resolution Assist, the insight cards themselves, rules-only mode, and any answer that fails the checks in step 7, because it falls back to rules with no retry.

Easy to miss

Phase 3 evaluation and red-team runs. Phase 4 shadow mode, where every answer is generated and paid for but not shown. Follow-up questions, which send the current thread again.

Try your own numbers

What would multiply it
  • Letting the model call tools itself. Each tool round trip resends everything so far. In the prototype's tool flow (1–4 tools per question), that comes to roughly 11k input and 1k output per question: about 2.5× the input of this design.
  • Sending raw data: a whole queue or history rows instead of named fields and totals.
  • Long threads. Cap the turns per thread, or start a new thread per ticket.
  • Reasoning output on models that think before they answer.
What keeps it low
  • Rules answer what they can. Explorer, Template search and data-table lookups never call the model.
  • A fixed prompt prefix (instructions and schema) that the gateway can cache.
  • Choose the model per intent: a smaller tier for lookups and a larger one only for handovers and deep dives.
  • Per-user and per-day token budgets at the gateway, with the kill switch when they're exceeded.
09 · Open questions

To confirm before Phase 0 closes

  1. Which approved model and gateway? The prototype lists Claude models only as placeholders. Production uses whatever Citi's gateway exposes for this data classification.
  2. Can ticket descriptions be sent at all? If not, Copilot can still answer KB and policy questions with AI, while ticket questions stay rules-only (the "Data allowed to send?" branch).
  3. Where is history stored? SC Lakehouse or another approved store, to keep Explorer, Template search and Resolution Assist working.
  4. ServiceNow access. A read-only integration user for the tools, and a separate approved path for write-back.
  1. Search technology. Is the keyword search good enough, or is an approved vector or search service available? It would replace step 3 only.
  2. Evaluation thresholds. Which accuracy, citation and refusal rates does model risk want for the pilot?
  3. Audit retention. How long prompts and answers are kept, and who can read them.
  4. Labelling. Required wording and placement for "AI-generated" in the UI.
  5. Token chargeback. What the gateway charges per million input and output tokens for the approved model, whether prompt caching is passed through, and what quota the intake record should request (the expected case in section 08 is ~31M input and ~3M output a month).
